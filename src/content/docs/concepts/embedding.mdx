Until 0.3 a `UdcDataView` was a page: a title, tabs, a toolbar, the rows in a card, and the query
string to itself. From `@jsudc/react` 0.4.0 it can be one pane of a host's screen: the message
list of a mail client between its folder list and its reading pane. Every prop below is
optional; without them the view is what it always was.

| Prop                         | What it does                                                                                                                                                                         |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `filter`                     | a `FilterNode` of the host's (the open folder), ANDed into every list the view and its renderers load and counted in "of M"; not a chip or pill, not in the URL, not removed by "clear filters" |
| `chrome`                     | which parts of the frame are drawn: `"full"` (default), `"embedded"`, or flags                                                                                                     |
| `pagingMode`                 | the paging mode to open in, instead of the view's `pagination`                                                                                                                       |
| `toolbarStart`, `toolbarEnd` | the host's own controls at the start (before the search) and at the end (after the count) of the toolbar                                                                           |
| `urlPrefix`                  | a prefix for every parameter the view and its renderers read and write                                                                                                               |
| `urlState`                   | `"url"` (default: the adapter in effect), `"memory"`, or any `UrlStateAdapter`                                                                                                     |

## The host's filter

The host's filter is what the host decides and the user does not: the folder, the account, the
project. The user still searches, picks chips and builds filters on top of it; "Clear" and
"Clear filters" remove theirs and leave the host's; an empty folder shows "no rows", not "no rows
match, clear filters". It reaches every renderer through `filter` and `baseFilter` of
[`RendererProps`](#a-renderer-of-the-hosts-the-rendererprops-contract), so the kanban, the
calendar, the tree, the map and the chart load the folder's rows too. Change it and the view asks
again; an equal object passed anew on each render asks nothing.

The host's filter is a convenience of the screen, not a security boundary: whatever a user may
not see, the server holds them to with a [row scope](/concepts/request-context/).

## Chrome switches and toolbar slots

`chrome` is a preset or flags, `true` drawing the part; a flag left out takes the preset's value
(`full`: all on, `embedded`: all off).

| Flag           | The part                                                                                                                         |
| -------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| `header`       | the title and the description                                                                                                    |
| `tabs`         | the renderer tabs (with Doc or Source still on, the renderer in use stays as the way back)                                       |
| `pagingToggle` | the pages / infinite switch; without it the mode is `pagingMode`, else the view's `pagination`, never a stored choice or `?mode=` |
| `docTab`       | the Doc pseudo-tab (the collection's README)                                                                                     |
| `sourceTab`    | the Source pseudo-tab (the source file)                                                                                          |
| `frame`        | the card around toolbar and rows: border, rounding, shadow and the outer margins                                                |

`chrome="embedded"` leaves the toolbar and the rows only; `chrome={{ preset: "embedded", tabs:
true }}` adds the tabs back, as in the example. The parts keep their stable classes
(`udc-data-view`, `udc-toolbar`, …; see [Theming](/concepts/theming/)).

`toolbarStart` and `toolbarEnd` take any React node: a Compose button before the search, a Sync
button after the count.

## URL state: a prefix, or in memory

By default the view's parameters are the page's own (`?q=`, `?sort=`, `?tab=`, …), which is right
for a view that is the page. A pane shares the query string with its host and maybe with other
views:

- **`urlPrefix="inbox."`** makes the view and its renderers use `inbox.q`, `inbox.sort`,
  `inbox.p`, `inbox.board`, `inbox.win`, … and leave every other parameter alone. A host route
  with a `?q=` of its own is neither read nor removed, and two views with different prefixes keep
  separate search, sort and page on one page. End the prefix with a separator: every key that
  starts with it is the view's.
- **`urlState="memory"`** keeps the view's state in a store of its own: the address bar is never
  touched, and a reload starts afresh.
- **`urlState={adapter}`** uses any `UrlStateAdapter` (a host store, a router adapter);
  `urlPrefix` applies on top of it.

Both are adapters, exported from `@jsudc/react` and `@jsudc/react/headless` for a host's own
components: `prefixUrlStateAdapter(inner, prefix)` wraps any adapter and reads and writes only its
own keys, and `createMemoryUrlStateAdapter(initial?)` is a query string in memory. Because the
prefix applies at the adapter, every parameter is covered, the kanban's, the chart's and the
calendar's included. The host's own controls of a pane can share the view's parameters:

## A renderer of the host's: the `RendererProps` contract

A host draws rows its own way (a message list, a timeline) by registering a renderer of its own;
`UdcDataView` hands its `component` the props below. From 0.4.0 they are a **public contract**:
none of them is renamed, removed or retyped outside a major release, and a prop added later is
optional, so a renderer written today keeps compiling. (`@jsudc/react` compiles a host-written
renderer against its published declarations on every build.)

| Prop                                 | Type                                       | What it is                                                                                                        |
| ------------------------------------ | ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------- |
| `collection`                         | `string`                                   | the collection's name                                                                                             |
| `describe`                           | `DescribeResponse`                         | its schema, view and capabilities, soft-deleted fields already gone                                               |
| `data`                               | `UdcCollectionResult`                      | the view's paged list (`rows`, `total`, `isLoading`, `error`, `hasNextPage`, `fetchNextPage`, …); loaded only when `paging: true` |
| `filter`                             | `FilterNode \| undefined`                  | everything that filters the rows, composed: the host's `filter`, search, chips, the filter tree, the chart window |
| `baseFilter`                         | `FilterNode \| undefined`                  | `filter` without the search, for a renderer that searches what it loaded                                          |
| `unwindowedFilter`                   | `FilterNode \| undefined` (optional)       | `filter` without the chart window: what "of M" counts                                                             |
| `chartWindow`                        | `ChartWindowState \| undefined` (optional) | the chart window when one applies (already in `filter`)                                                           |
| `search`                             | `string`                                   | the search box as typed (for highlighting)                                                                        |
| `sort`, `onSort(field, multi)`       | `SortKey[]`, function                      | the sort and the header click that cycles it                                                                      |
| `mode`, `page`, `limit`, `onPage(n)` | `"pages" \| "infinite"`, numbers, function | the paging mode, the 1-based page, the page size, go to a page                                                    |
| `filtered`, `onClearFilters()`       | `boolean`, function                        | did the user filter (the host's `filter` does not count), and "clear filters" for the empty state                 |
| `resetKey`                           | `string`                                   | changes whenever the rows mean something else: scroll back to the top on it                                       |
| `onCount(count \| null)`             | function                                   | a renderer with `paging: false` reports what the toolbar's "Showing N of M" says                                  |
| `onSchemaAction`                     | function (optional)                        | set when the schema may be edited and the renderer has `editMode`                                                 |
| `folder`                             | `FolderNav \| undefined` (optional)        | set when the view has `folder_options`                                                                            |
| `onRowActivate`, `activeRowId`, `onActiveRowChange` | optional                    | set only when the host turned [row activation](/concepts/views/#row-activation-and-the-keyboard) on               |

A renderer with `paging: true` draws `data` and needs nothing else; one with `paging: false` loads
its own rows with `filter` (the hooks of `@jsudc/react/headless`, e.g. `useUdcAllRows`) and
reports `onCount`. The message list the example registers:

## The scoped stylesheet

`@jsudc/react/styles.css` is made for a page that is the library's: its preflight resets every
`h1`, `button` and list of the page, its `body` rule sets the page's font and colours, and its
tokens sit on `:root`, where they overwrite a host's own `--background` or `--primary`. A host
that embeds a view in pages of its own imports the scoped sheet instead (one of the two, not
both): `import "@jsudc/react/styles.scoped.css"`, as `Mail.tsx` above does, or from the host's CSS:

```css
@import "@jsudc/react/styles.scoped.css";
```

It has the same utilities, tokens and resets, applied only inside the library's roots:
`.udc-data-view`, and `.udc-scope` (`UDC_SCOPE_CLASS`), which the default UI kit puts on
everything it portals out of the view (dialogs, popovers, menus, selects, tooltips, toasts). There
is no rule on `*`, `html`, `body` or `:root`, no global preflight and no `@property`
registration, so the host's elements compute exactly the styles they computed before.

| Situation                                                                | Sheet               |
| ------------------------------------------------------------------------ | ------------------- |
| the page is the library's (an admin, a back office), or a new app        | `styles.css`        |
| the view is a pane of the host's own pages, with the host's own base CSS | `styles.scoped.css` |
| the host's tokens share the generic names (`--background`, `--primary`)  | `styles.scoped.css` |

What changes with it:

- **Theming:** the tokens are declared on the roots at zero specificity, so the host restyles the
  library on the roots, not on `:root`: `.udc-data-view, .udc-scope { --primary: …; }`. `.dark` on
  any ancestor still switches the theme.
- **Components outside a view:** a `LookupCombobox` or a schema dialog the host renders outside
  `<UdcDataView>` needs a root around it: an element with `className={UDC_SCOPE_CLASS}`.
- **The background:** a root paints none; the view sits on the host's pane.
- **The cascade:** the resets are in `@layer base` and the utilities in `@layer utilities`, so an
  unlayered element rule of the host (`button { background: … }`) still reaches inside the view.
  Put the host's own base styles in a layer, or scope them, if they should not.
